### Database restore rehearsal

Only the disposable `nyan_shop_bot_test` database was used. A synthetic `{}` catalog-curation row was inserted there, then `pg_dump -Fc` created a custom archive. A new `nyan_shop_bot_restore_nsb031` database was created from `template0`, and `pg_restore --exit-on-error --no-owner --no-privileges` completed. Source and restored database both reported Alembic revision `20260924_0003` and one catalog-curation row; both had the same six public tables. The synthetic source row, restore database, and temporary archives were removed afterward. The saved `nyan_shop_bot` database was only queried for counts (one curation document, four mock orders), never dumped, reset, or modified during this rehearsal.

This proves a basic local logical restore with a synthetic row. Before staging or live use, a separately approved run must restore an encrypted backup into an isolated environment, check application-level invariants and access controls, measure recovery time and data loss, test migration rollback or forward recovery, and document retention and key custody. PostgreSQL documents the [custom archive format](https://www.postgresql.org/docs/17/app-pgdump.html) and [restore into a newly created database](https://www.postgresql.org/docs/17/app-pgrestore.html).

### Two-source rollout sequence

KhoMMO and VietShare have separate technical gates. For **each** source: verify the versioned order/status/delivery contract without committing private partner material; build an offline injected-transport conformance suite for accepted, rejected, duplicate, timeout, crash, and status-lookup outcomes (including 202 for VietShare); prove one persisted request identity and no second obligation; then run an owner-approved capped test in the supplier's permitted environment. A successful test of one source does not enable the other. Roboticvn remains outside this two-source sales target.

The catalog may show offers from both sources, but source selection must be server-authoritative for each approved Nyan listing. A source outage can prevent a new order or hide availability. After an attempt begins, switching source is a new commercial action and must never be used as automatic recovery from `UNKNOWN`.

### Capped supplier test gate (draft, NOT RUN)

Each supplier needs a separate test authorization after its offline conformance suite passes. The reviewable test spec must name the partner account, one exact catalog product/variant and quantity, a maximum integer spend with explicit currency, the funded wallet or supplier-side account limit, test window, operator allowlist, kill-switch owner, expected order identity, status lookup, and how delivered credentials will be handled without logging them. Customer payment must remain disabled. The operator must check wallet balance and order history before and after, record only redacted identifiers and amounts, and stop on the first uncertain outcome.

VietShare can use its documented `max_unit_price` and stable Idempotency-Key, but the first live test must still prove replay and 202 handling within the approved worst-case spend limit. KhoMMO has no documented purchase price ceiling or idempotency guarantee in the reviewed page; its first test must be one attended POST only, with a supplier-enforced or otherwise verifiable wallet/account spend cap. A lost response stays `UNKNOWN`; no second POST is permitted while the obligation is unresolved. If a real bound on possible spend cannot be shown, the capped KhoMMO test is not ready. Neither test is authorized by this document.

## Payment and order decision to make

For digital goods sold **inside Telegram**, Telegram's [official Stars payment guide](https://core.telegram.org/bots/payments-stars) requires `XTR`. An invoice must be tied to an immutable shop intent; `pre_checkout_query` must validate it, while fulfillment waits for a persisted `successful_payment` update. An accepted pre-checkout query alone is not payment evidence. Duplicate updates and forwarded or reusable invoices need one-to-one or explicitly bounded payment identity. The current VND catalog price is not an XTR amount; no conversion or Stars price has been approved. A separate website payment route, if desired, needs its own later spec and regulatory/settlement review.

Telegram documents a [separate test environment](https://core.telegram.org/bots/features#testing-your-bot) with a separate account and bot. A future test issue should keep that bot/token outside source, CI, logs, and screenshots; test invoice creation, rejected pre-checkout, successful payment, duplicate `successful_payment`, refund/support handling, and interruption before fulfillment. That test has **NOT RUN**. No current bot route sends an invoice or calls Telegram payment transport.

Before either supplier purchase implementation can be enabled, the source-specific settlement model and a capped test specification must be approved. Each source-specific spec must pin server-authoritative supplier identity/price/stock, persist a stable request identity before outbound work, define a verified status lookup, and leave timeout/202/crash outcomes `UNKNOWN` until reconciled. Never retry with a fresh supplier identity, switch supplier to resolve an uncertain order, or deliver credentials on an unconfirmed payment/purchase. Keep payment receipt, supplier obligation, and customer delivery as separate durable states.
